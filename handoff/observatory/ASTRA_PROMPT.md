## 4. 接入协议与启动

从原始 ZIP 解压并校验，执行 `docker load -i flightgen-image.tar`。发生器参考启动配置：

```sh
docker run -d --name object-source \
  --cpuset-cpus=0 --cpus=1 --memory=256m --memory-swap=256m \
  -p 127.0.0.1:9001:9001 \
  -v "$PWD/generator-runs:/runs" \
  talkingdata/flightgen:exam-v4-f1
```

启动 POST /start，控制样例：

```json
{
  "workload": "objects",
  "target_url": "http://host.docker.internal:8000/ingest",
  "test_id": "run-001",
  "seed": 42,
  "batch_size": 20,
  "workers": 4,
  "objects_per_second": 200,
  "rate_profile": "bursty",
  "ramp_seconds": 10,
  "duration_seconds": 120,
  "max_batches": 20000,
  "retries": 2,
  "objects": {"scenario": "evolving", "tree_every_batches": 10}
}
```

每轮使用新的 test_id。GET /status；POST /rate 可改 objects_per_second；0 表示尽力发送，不是暂停。POST /stop 返回 202，需轮询外层 state=finished 后 GET /receipt，否则可能 409。运行中再次 start 返回 409。

发生器向 target_url 发送 POST。任意 2xx 表示「整条消息已可靠保存」；非 2xx/超时可能重试；部分发送依赖前序确认。接收端监听可被容器访问的地址，容器服务发布端口；也可使用经验证的 Compose 服务名通信。发生器控制端口绑定 localhost。

样本结构（省略号只用于说明，非 JSON 字面值）：
- types: `{kind:"types", test_id, revision, changes:[{op:"create|rename|move", node:{type_id,parent_id,name}}]}`
- objects: `{kind:"objects", test_id, batch_id, tree_revision, objects:[{id,sequence,type_id,name,timestamp_ms,position,attributes}]}`
- position: `{frame_id,frame_kind,unit,x,y,z}` 或 null。

## 5. 建议技术方案与实现边界

默认采用 Python + FastAPI + SQLite WAL，React + TypeScript + Vite。前端用 Canvas2D 或熟悉的轻量图表库，避免为此引入复杂 3D 引擎。多阶段 Docker 构建前端静态产物，由后端统一提供；生产运行尽量只有一个应用服务及独立发生器。选择已验证支持 arm64 的依赖，固定依赖版本并保存锁文件。若已有可靠脚手架可复用，说明取舍，不重搭基础设施。

### 数据与可靠性

- 索引固定字段，动态 attributes 保留 JSON；不要为所有属性建列，不要凭观察值自动确定永久 schema。
- 逻辑实体包括运行、收到的消息/批次、类型和类型变更、对象、异常记录。实际表结构由你用最少必要表实现。
- run/test_id 纳入所有相关主键、去重和查询条件，避免不同运行的 batch_id/type_id 相互覆盖。
- 采用事务、参数化 SQL、受控写入并发、busy_timeout；WAL 之外要明确同步策略。若声称可靠落盘，默认 synchronous=FULL，记录平台与文件系统的保证边界。
- 简单路径：整条消息的持久记录、对象/分类更新、去重信息在同一事务提交后返回 2xx。不要先返回 200 再异步保存到内存队列。
- 若采用持久收件箱再异步投影，必须实现重启恢复、队列上限、积压可见和可重放；没有时间证明这些就使用同步事务。
- 重复消息不能重复计数；相同业务消息键但内容不同必须检测为冲突，不能一律吞掉。设计哈希比对和隔离/拒绝策略，并说明按原始字节还是规范化 JSON 比较。
- 对重复对象 ID 的冲突/更新语义先调查，再明确采用的规则；不能假定 sequence 就是对象更新版本，也不能凭最后到达覆盖。
- 分类按 revision 处理。重复版本幂等；乱序/缺口不能静默标记为已应用。可明确拒绝并记录，或持久等待并恢复，但避免复杂无界缓冲。未知 op/未知类型要可观测。
- 明确当前分类视图与历史 tree_revision 的区别；类型迁移后当前子树筛选应正确。保留原始版本信息，不要求两小时实现历史时间旅行。
- 异常策略必须清晰：建议异常消息整体持久隔离，不混入正常对象，然后可以按“已可靠保存”返回 2xx；或者完整拒绝且没有部分写入。不要部分入库后整批假成功。标明选择及影响。
- 不把业务属性中数值/字符串/null的变化一律当坏数据；严格校验消息骨架，保留未知属性。
- 请求体有可配置上限，查询分页/数量上限、写锁等待有界；服务过载可明确返回 429/503。磁盘不足不能确认成功。
- 持久化预算包含 DB、WAL、日志和隔离数据；设置软水位/停止接收策略与轮转日志，注明 Compose volume 不会自动限制到 20 GiB。磁盘满的错误路径不能返回 2xx。

### 查询与性能

- 对运行、类型、对象 ID、分页排序等必要字段建索引；使用有上限的查询和分页，优先游标分页。
- 提供类型树、对象列表/详情、基础检索、空间点采样、运行指标 API。
- 列表响应不返回全部长描述，详情按需读取；不要把全库载入 Python 或浏览器。
- 不要求任意深度 JSON 属性全局索引或全文检索；若实现基础名称搜索，说明索引能力与规模限制。
- 指标使用增量计数或适当缓存，避免每次轮询扫全表。
- 空间采样数量有上限（如 2,000～5,000，按实测调整）；选择有界可解释的采样方式，不用大表 ORDER BY RANDOM()。标注采样/最近点，不能冒充全量分布。
- 写入、读取同时进行时测延迟；单纯接收成功率不足以证明系统可用。

### 界面与可视化

产品方向：清晰、精致的实时观测工作台。左侧分类树，中间对象列表/空间视图切换，右侧对象详情；顶部简洁展示运行、有效对象量、接入速率和异常情况。主工作区有视觉重点，不要用大标题和无用卡片占满屏幕。

必需交互：选择运行 → 展开/选择分类（明确含不含后代）→ 筛选/分页 → 点击对象查看详情。分类变化有可见记录；动态属性以可展开结构展示，长文本折叠。状态必须覆盖无数据、加载、失败、断连/陈旧数据。指标来自真实后端。

空间视图严格限定同一 frame_id/frame_kind/unit，标明 X/Y 投影及原始单位，不能混合光年和米，也不能把局部 x/y 当经纬度。无坐标对象仍可列表探索。支持点选详情、简单缩放或筛选；坐标视图不承诺真实天文定位。

分类分布、时间速率图与空间图优先使用简单可解释图形。时间趋势区分数据 timestamp_ms 与系统接收时间；样本业务时间不等于运行当前时间。

视觉建议：克制的深色或浅色科学仪表台、单一主强调色、清晰中文字级、紧凑对齐和良好对比度。无强制生成图片、外部字体或付费资源。优先代码原生 UI，不走耗时设计图审批。桌面完整，小屏面板折叠可用。可用 1–2 秒轮询，避免每条对象推送导致重渲染。

## 7. 必须实际执行的验收

### 正确性和可靠性

1. 接入真实发生器的 evolving 场景，确认 types 与 objects 被正确处理。
2. 重放同一批次，正常对象数和业务统计不重复增长。
3. 同一消息键不同内容，能检测冲突，已有结果不被默默覆盖。
4. 分类 create/rename/move 后树结构、对象详情与子树筛选一致；重复/缺口版本行为符合策略。
5. 缺少 type_id、attributes=[]、无效 JSON 按明确规则处理，无部分写入/假确认。属性类型变化本身可正常展示。
6. 重启或强制停止应用后重新启动，已经确认的数据仍可查；重放不重复。清楚区分进程崩溃测试与未测试的主机断电保证。
7. 两个不同 test_id 有相同 batch_id/type_id 时互不污染。
8. 过滤/查询参数非法、未知对象 ID、空数据，返回可解释结果，不导致服务崩溃。

用少量针对这些失败模式的自动化测试，不堆无意义覆盖率。重启前记录已确认消息与对应对象/隔离记录，恢复后对账；不能只看到某条旧数据就称“零丢失”。

### 性能

在规定资源限制下运行至少两档或尽可能三档短测，例如目标 200、2,000、10,000 对象/秒；这些是探索档位，不是必须达到的承诺。根据发生器与系统实际能力调整，若发生器是瓶颈就明确记录，不能宣称测得系统上限。不要用 rate=0 误当暂停。固定并记录 seed/batch_size/workers/profile/时长/预热及数据初始规模，每轮新 test_id。

记录：目标速率、实际确认速率、有效入库量/速率、重复/异常/拒绝量、请求延迟（能测则 p50/p95）、并发查询延迟、CPU、峰值内存、DB+WAL+日志增长，以及发生器资源。实际确认请求和对象计数、故障注入计数、唯一有效对象数分别报告。使用状态/收据与数据库证据对账；若只测了汇总计数，就不要写成完整逐对象证明。

保存原始收据和机器可读结果。README 只写实际运行所得，注明短测和规模边界，不能把采样数据或 target_objects_per_second 写成达成吞吐。未测满 20 GiB 或未测百万对象就明确未测。

### 界面与部署

- 浏览器真实加载并操作：分类选择、搜索/过滤、翻页、对象详情、空间 frame 切换；查看 console 与页面错误。
- 至少保存桌面截图，检查一个窄屏布局；页面展示真实发生器数据。
- 在 Linux arm64 Docker 中构建并启动，确认健康检查、端口和持久化挂载。
- 检查实际容器资源配置，而不只是 Compose 文本。
- 文档启动流程不能依赖我的临时 /tmp 路径、已存在容器或你个人的 Python venv。
- 提供附件自动下载/校验/导入脚本，或可复现的附件准备命令；不要要求评审手动复制数据内容，不要将 Docker 镜像/运行 DB 意外提交到源码仓库。
