# 演示与面试说明

## 三分钟演示

1. 选择一次真实发生器运行，解释对象总数与消息数的区别。
2. 展开分类、选择含后代的子树，再用名称前缀或对象 ID 定位。
3. 在列表点开对象，展开嵌套属性；说明未知字段也完整保存。
4. 切换坐标框架，旋转点云、选中一个点并聚焦。说明点云数量上限和原始单位。
5. 下载筛选结果 NDJSON，展示完整属性和导出记录数。
6. 打开异常消息，展示原始体与整批隔离原因。
7. 指向真实混合负载与 SIGKILL 恢复收据，解释测量口径与边界。

## 关键问题

**为什么不能入内存后返回 200？** 发生器把任何 2xx 都看成整条消息已经可靠保存。进程可能在队列处理前退出，因此必须以持久事务提交作为确认边界。

**为什么既要消息去重，又要对象唯一键？** 消息重复是重试，同一对象出现在新的消息中是另一种情况。把两者混在一起会重复计数或丢掉合法观测。

**为什么不直接采用 sequence 最大的对象？** 样本只证明字段存在，没有证明它是更新版本。当前对不同内容明确隔离，等待协议证据再引入更新规则。

**分类迁移会影响什么？** 当前树和子树筛选随 revision 更新；对象仍指向稳定 type_id。迁移不要求重写所有对象。历史原始消息保留当时 tree_revision。

**为什么所有动态字段放 JSON？** 字段数量多、嵌套且类型可能变化。固定查询字段单独索引，其余 JSON 保留原貌，兼顾可查与可扩展。

**为什么不把所有对象发到浏览器？** 网络、布局与 GPU 都有成本。分页和有界点云让探索成本可控，全量输出走流式接口。

**SQLite 的限制是什么？** 写事务串行；持久化与索引维护会限制吞吐。WAL 改善读写并发，但慢读事务可能阻碍 checkpoint，所以导出使用分块短查询。

**实测能证明什么？** 只证明记录的环境、规模、持续时间与查询组合下的行为。目标发生速率不等于实际确认速率；确认保存与有效对象数也有不同口径。

**再给一天优先做什么？** 先扩大数据规模和持续时间定位瓶颈，再根据真实协议补充对象更新语义与隔离重放；增加持续容量告警和备份恢复验证。只有出现证据支持的吞吐瓶颈，才引入持久收件箱异步投影或更重的存储组件。
